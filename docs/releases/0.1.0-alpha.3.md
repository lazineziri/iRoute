# iRoute 0.1.0-alpha.3

- Release date: 2026-08-18
- Channel: alpha prerelease
- Public API: v1

This release makes routing claims auditable and closes five workflow lifecycle,
policy, accounting, and approval-concurrency gaps found during a review of the
published `0.1.0-alpha.2` source.

## Why upgrade

Built-in model profiles previously described deterministic evaluation inputs as
measurements. Profiles now explicitly identify their values as `Synthetic`,
`Unverified`, or `Measured`; a measured profile is routing-eligible only when it
has a valid provider, model, measurement timestamp, and positive sample count.
That provenance is preserved in routing decisions and official SDK contracts.

The runtime also no longer strands executions when submission setup fails after
the durable insert, rejects valid model-first read-only plans, loses model usage
behind tool steps, or allows concurrent inline approval replays to execute the
same plan twice.

## Breaking source and extension changes

`ModelProfile.MeasurementSource` is now a `ModelProfileSource` enum rather than a
free-form string. Code that constructs profiles must use `Synthetic`,
`Unverified`, or `Measured`; measured profiles must also provide a
`ModelProfileMeasurement` record.

Custom `IExecutionStore` implementations must implement `TryTransitionAsync` as
an atomic compare-and-set of the persisted execution status. The built-in
in-memory, SQLite, and PostgreSQL stores implement it. This is a prerelease
source-extension change; the HTTP v1 changes remain additive.

## Fixed

- Failure or cancellation while appending the initial `created` event now
  terminalizes the inserted execution, allowing idempotent retries to observe a
  final outcome instead of replaying `Accepted` forever.
- Approval-required multi-step plans select the plan-wide action step and create
  a durable approval instead of failing through a single-step assumption.
- Policy evaluates effective side effects across the plan and uses the last
  matching action step, allowing model-first read-only workflows.
- Usage, evidence, model metadata, and budget enforcement aggregate every
  completed workflow step exactly once, including model-to-tool and
  model-to-tool-to-model chains.
- Inline approval resumption atomically claims `WaitingForApproval -> Running`,
  making identical concurrent approvals idempotent across runtime instances.

## Upgrading and rollback

No database migration is required. Upgrade runtime components and SDKs together
when relying on the new provenance fields. Custom stores must implement the
atomic transition contract before enabling inline approval resumption.

To roll back, restore the previous runtime and SDK versions. Stored state is
compatible because this release adds no schema migration. Do not move or replace
the signed tag or published packages; publish a new prerelease for corrections.

## Known limits

This remains an experimental alpha intended for evaluation and controlled
pilots. Breaking changes are expected before `1.0`. There is no production SLA
and no security-response SLA.

The reference connectors are not production integrations. Built-in profile
quality, cost, and latency values are synthetic evaluation inputs.
They are not validated production measurements.
Deployments that require separation of duties must enforce it in their
identity/policy layer; the runtime does not yet
prohibit a requester from approving the requester's own action.

Tenant quotas, rate limiting, request-body limits, sustained load and soak
testing, and production failover validation remain ahead.
Self-hosters are responsible for database operations, network security, identity, provider
credentials, backups, and review of approved external actions.

Verify the downloaded `SHA256SUMS` and `release-manifest.json` before installing
artifacts from the GitHub prerelease.
