# iRoute 0.1.0-alpha.2

- Release date: 2026-08-03
- Channel: alpha prerelease
- Public API: v1

This release is a correctness pass over `0.1.0-alpha.1`, driven by a full review
of the published repository. The public contract is unchanged apart from one
additive event type; the changes are in behaviour that the previous release
described accurately but did not deliver.

## Why upgrade

`0.1.0-alpha.1` could not complete its own documented quick start. The API and
the worker both defaulted to a relative SQLite path, and because `dotnet run
--project` sets the working directory to the project folder, the two hosts opened
different databases. Every submission stayed `Queued` while the worker polled an
empty file. Only the container profiles, which share a volume, worked.

Alongside that, two writes racing each other could destroy data: cancelling an
execution that had just finished reverted its status and erased the recorded
outcome, and a cancellation that arrived mid-execution was overwritten by the
worker's next transition, so it was silently ignored.

Both are fixed, along with an unknown `taskType` returning HTTP 500, an
idempotent retry returning HTTP 500 when it raced the original, and a repeatedly
failing execution being redelivered roughly once per second forever.

## Breaking changes

**`Storage:Provider=Memory` is removed.** It kept no durable record, so an
execution could not survive a restart and approvals, leases and artifacts went
with the process. It had neither migrations nor a health check, so it was never a
deployment target, but it was documented as a peer of the durable providers.
Configuring it now fails at startup. Use `Sqlite` for single-node development or
`Postgres` to deploy.

**The Node.js SDK is published as `@iroute-dev/sdk`.** The `@iroute` npm scope
belongs to an unrelated account. Replace the dependency name; the API is
unchanged.

**Node.js `24.18.1` is the single declared floor.** The previous release declared
`24.18.1` in `release.json` and CI while the root tooling and the SDK README
claimed `22.20.0`, so adopters could not tell what was supported.

## Upgrading

A relative SQLite data source is no longer resolved against the host's working
directory. It resolves against one per-user directory shared by every iRoute host
on the machine, so the API and worker agree regardless of where each was started:

| Platform | Location |
|---|---|
| macOS | `~/Library/Application Support/iRoute` |
| Linux | `$XDG_DATA_HOME/iRoute`, or `~/.local/share/iRoute` |
| Windows | `%LOCALAPPDATA%\iRoute` |

To keep an existing development database, move `iroute.db` there or set
`ConnectionStrings__iRoute` to its absolute path. Deployments that already pass
an absolute path or a PostgreSQL connection string are unaffected.

The schema adds one nullable column, `Executions.InputFingerprint`, applied by
migration `20260802120000_IdempotencyFingerprint`. Executions recorded before the
upgrade have no fingerprint and are still treated as retries, so upgrading cannot
start rejecting idempotency keys that previously worked.

## Added

Operators can now resolve an external action whose outcome is unknown. When a
worker stops mid call, iRoute cannot tell whether the side effect happened, so it
refuses every later attempt rather than risk firing an irreversible action twice.
Previously nothing could release that reservation and the execution was wedged
permanently. `GET /v1/executions/{executionId}/external-actions` lists unresolved
reservations, and
`POST /v1/executions/{executionId}/external-actions/{actionId}/reconcile` records
what actually happened. Both require the `approval:grant` scope. Recording
success makes a resubmission with the same idempotency key reuse the result;
recording failure allows another attempt. Either decision appends the new
`external_action.reconciled` event.

Reusing an idempotency key with a different payload now returns `409` with
`idempotency_key_conflict`, which the OpenAPI document has always declared.

`ExecutionWorker:MaxDeliveryAttempts` (default `5`) and
`ExecutionWorker:MaxAbandonDelay` (default `5 minutes`) bound redelivery of an
execution that cannot succeed. Setting the first to `0` restores unbounded
redelivery.

## Fixed

- Durable writes made while processing a leased execution are verified against
  the owning lease inside the transaction that performs them, so a worker whose
  lease was taken over can no longer interleave writes with the new owner.
- The SQLite container profile binds to loopback. It trusts unauthenticated
  identity headers and previously listened on every interface.
- Event streaming no longer times out after 30 seconds in the Python SDK, and no
  longer blocks indefinitely in the Java SDK.
- `problem.schema.json` lists the six capability error codes the runtime emits;
  a validating consumer previously rejected them.
- `cargo publish --locked` can run: `sdks/rust/Cargo.lock` is committed.
- The documented installation sequence passes. SDK conformance runs against
  whichever configuration was built, and reports failure when no runner executed
  instead of claiming success.

## Known limits

This remains an experimental alpha intended for evaluation and controlled
pilots. Breaking changes are expected before `1.0`. There is no production SLA
and no security-response SLA.

The reference connectors are not production integrations, and `email.send`
remains simulated and approval-gated. Checked provider cost, quality and latency
figures come from the deterministic evaluation harness and are
not validated production measurements.

Self-hosters are responsible for provisioning and operating the database,
securing network exposure, supplying provider credentials, and reviewing every
external action their tenants approve.

Tenant quotas, rate limiting, request body limits, sustained load and soak
testing, and production failover validation are still ahead. Run one lifecycle
worker per database; execution workers scale horizontally on PostgreSQL.
